## What I built

### Rate-limit gate (new: `apps/api/specula_api/ratelimit.py`)
- `_InProcessLimiter` — per-user **cooldown** (`settings.run_cooldown_s`) + **sliding 1-hour
  window cap** (`settings.run_rate_limit_per_hour`). Pure, clock-injected (`now` arg) for tests.
- `enforce_rate_limit(user_id)` / `rate_limit_guard` (dependency form) — read the two settings +
  a module-level `_clock` seam, record a trigger or raise `RateLimited(retry_after_s)`.
- `RateLimitedRoute(APIRoute)` — renders any `RateLimited` (raised by a dependency **or** in a
  handler body) as a **bare** 429 matching the frozen `RateLimitError` shape
  `{"error":"rate_limited","retryAfterS":<int>}` + a `Retry-After` header.

### Wiring
- `routers/run.py` — `POST /runs` gets `Depends(rate_limit_guard)`; router uses
  `route_class=RateLimitedRoute`.
- `routers/approval.py` — `enforce_rate_limit(user_id)` is called **only at the approve→ingest
  trigger** (`company_id is not None`), so cheap reject/snooze decisions are never throttled.
  Router uses `route_class=RateLimitedRoute`. A rate-limited approve raises before commit, so
  `get_session` rolls the decision back — the approval stays undecided and a retry re-applies it
  and triggers the ingest together.

## Design decisions the integrator should know
- **Runs and ingests share one per-user trigger budget.** Both are heavy pipeline triggers;
  `run_rate_limit_per_hour` / `run_cooldown_s` bound them together.
- **Bare-body rendering without touching `main.py`.** The frozen `RateLimitError` body cannot be
  produced by FastAPI's default `HTTPException` handler (it wraps in `{"detail": ...}`), and the
  app-level exception-handler seam lives in `main.py`, which **OBS owns exclusively**. I used a
  per-router `route_class` so the rendering stays entirely in NET's files — **no `main.py` edit,
  no global handler, no conflict with OBS.** Note for OBS: `RateLimited` is converted to a 429
  inside the route handler *before* any app-level middleware, so a Sentry/error hook will not see
  it as an error (correct — a throttle is not an exception to report).

## Deferred (needs Redis, with hosting)
The limiter is **in-process / single-instance** and resets on restart. A durable, multi-instance
rate limit (shared across web replicas / a worker fleet) needs Redis — deferred with the
scheduler/hosting milestone, consistent with this milestone's inline execution.
